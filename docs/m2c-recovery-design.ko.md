# M2C-02a — 영속 편집 작업 기록의 계약

상태: 로컬 검토본 구현·독립 검사. 원격 서버에 설치되지 않았고 config/MCP에는 아직 연결되지 않았다. [진행표](progress.md), [검증 기록](validation/m2c-recovery-local.json).

## 선택한 범위
기존 M2c 메모리 중복 기록은 프로세스가 바뀌면 사라진다. 이번 계층은 완료된 편집의 영수증과 미완료 작업의 예약을 파일로 보존한다. 개발자가 지정한 workspace 밖 경로에 명시적으로 열고 Workspace에 주입한다. 기존 서버 기본값을 바꾸지 않는다.

같은 ID와 같은 요청의 성공 기록은 재전달할 수 있다. 실패·손상·미완료 기록은 자동 재실행하지 않는다. 다른 요청이 같은 ID를 사용하면 거부한다. 성공 재전달은 과거 작업 결과이지 현재 파일의 최신 내용 검사가 아니다.

## 기록 순서
1. 짧은 할당 잠금 아래 새 ID 디렉터리를 예약한다.
2. 시작 기록과 디렉터리를 동기화한 뒤 할당 잠금을 해제한다.
3. 변경 함수를 실행한다.
4. 허용된 편집 영수증을 검증하고 완료 기록을 임시 파일에 쓰고 동기화한다.
5. 완료 파일로 교체하고 디렉터리 동기화를 요청한 뒤 성공을 반환한다.

시작 이후 완료 기록이 없으면 active인지 interrupted인지 단정할 수 없다. 상태는 unresolved이고 실행은 거부한다. 파일 변경과 journal 완료는 단일 원자적 트랜잭션이 아니므로 파일이 바뀌었으나 결과를 모르는 구간은 반드시 남는다. 이 구간에서 성공을 꾸미거나 재실행하지 않는 것이 목적이다.

## 경계
- POSIX 로컬 파일시스템 전제. macOS와 다른 파일시스템의 실제 검증은 아직 없다.
- 상태 디렉터리는 소유자 전용이며 모든 지정 workspace와 겹치면 거부한다. 새 경로의 부모는 이미 존재해야 한다.
- 동일 journal·동일 ID 예약만 교차 프로세스 조정한다. 다른 ID 사이의 파일 수정 잠금은 여전히 프로세스 내부다.
- 할당 잠금이 강제 종료로 남으면 새 ID를 막고 운영자 검토를 요구한다. PID만 보고 훔치거나 TTL로 지우지 않는다.
- 자동 초기화·축출·재시도·롤백·프로세스 부활·원격 업로드 기능은 없다.
- 상대 경로·바이트 수·전후 해시 등 작은 영수증만 저장한다. 원문 파일, 수정 문자열, 예외 메시지를 저장하지 않는다. 해시는 암호화/서명 또는 강력한 비밀 보호가 아니다.
- 체크섬은 우발적 손상을 검사한다. 같은 OS 사용자나 악성 디스크가 유효한 기록을 위조하는 것은 방어하지 않는다.
- 호출 권한은 서버 공통 dispatch가 담당해야 한다. 직접 Workspace 사용은 권한 경계가 아니며 실제 서버 wiring은 후속이다.

## 검사와 내구성 해석
실제 Node 자식 프로세스의 효과 전/후/완료 기록 후 SIGKILL과 새로운 프로세스의 재요청을 검사했다. 실제 fsync 호출을 사용하지만 전원 차단이나 커널 패닉을 시뮬레이션한 것은 아니다. 성공한 콜백 기록은 전체 저장장치 내구성 보증이 아니다.

Node 공식 FileHandle.sync 문서도 동작이 운영체제와 장치에 의존한다고 설명한다: https://nodejs.org/docs/latest-v22.x/api/fs.html#filehandlesync (2026-09-19 확인). 서로 다른 파일의 변경과 journal commit을 원자적으로 묶으려면 별도 저장/트랜잭션 설계가 필요하다.

## 다음 수용 기준
운영자 설정에서 workspace 밖 상태 경로를 명시하고 config/selectWorkspace/SDK 경로에 연결할 것. 권한 회수 뒤 replay도 거부할 것. 시작·정상 종료·중단 후 상태 조회를 실제 SDK/서버로 검증할 것. 같은 ID의 미확정 상태는 자동 해제하지 말고 상태·실제 파일을 검토하는 운영 절차를 정의할 것. 그 전에는 이 기능을 배포된 서버의 재시작 복구 기능으로 표시하지 않는다.
